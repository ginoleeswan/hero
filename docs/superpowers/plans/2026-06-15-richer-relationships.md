# Richer Relationships (Lane 4) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add LLM-generated connection kinds (`love_interest`, `mentor`/`protege`, `rival`) — produced by Claude Code in-session — to a new authored `hero_connections` table, and surface them in a Connections section on the character screen (native + web).

**Architecture:** A new authored table `hero_connections` (mirroring the `hero_relatives` precedent) holds the AI edges with a kind `CHECK` constraint and a `confidence` score; a `get_hero_connections` RPC reads them. The derived `hero_relationships` graph and `rebuild_hero_relationships()` are untouched. A `relationships_ai_status` column on `heroes` is the generation ledger. A `getConnections` db helper + `useConnections` hook feed a new `ConnectionsSection` that reuses the existing `RelatedHeroStrip`. Edges are generated by Claude in-tab (documented runbook) and inserted via `execute_sql`.

**Tech Stack:** Expo / React Native, TypeScript (strict, no `any`), Supabase (Postgres + PostgREST RPC), TanStack Query, Jest + @testing-library, `mcp__supabase__apply_migration` / `execute_sql` / `generate_typescript_types`.

**Conventions:** Work directly on `master` (no feature branch). Screens never import `supabase`. `StyleSheet.create` for styles. Never use `Flame-Bold`. New tables need an RLS public-read policy. Run `yarn test:ci` for tests.

- [ ] **Step 1: Write the migration file**

```sql
-- Lane 4: richer relationships. AI-authored hero-to-hero connections live in their
-- OWN table (like hero_relatives), NOT in the derived hero_relationships graph — so a
-- rebuild can never destroy them and provenance is structural, not a WHERE clause.

create table if not exists public.hero_connections (
  hero_id        text not null references public.heroes(id) on delete cascade,
  related_id     text not null references public.heroes(id) on delete cascade,
  kind           text not null check (kind in ('love_interest','mentor','protege','rival')),
  rank           integer,
  confidence     real,
  cross_universe boolean not null default false,
  generated_at   timestamptz not null default now(),
  primary key (hero_id, kind, related_id)
);

-- RLS: enable + public read. Without the select policy, anon reads return 0 rows and
-- the RPC silently returns [] (project gotcha).
alter table public.hero_connections enable row level security;

create policy "hero_connections public read"
  on public.hero_connections for select using (true);

-- Read API — joined + ranked, same column shape as get_related_heroes so the client
-- reuses the RelatedHeroCard type. Plus confidence for future tuning.
create or replace function public.get_hero_connections(
  p_hero_id text,
  p_kind text,
  p_limit integer default 24
)
returns table (
  id text,
  name text,
  image_url text,
  image_md_url text,
  portrait_url text,
  publisher text,
  alignment text,
  rank integer,
  confidence real
)
language sql
stable
as $$
  select m.id, m.name, m.image_url, m.image_md_url, m.portrait_url,
         m.publisher, m.alignment, c.rank, c.confidence
  from public.hero_connections c
  join public.heroes m on m.id = c.related_id
  where c.hero_id = p_hero_id
    and c.kind = p_kind
  order by c.rank asc nulls last
  limit p_limit;
$$;

grant execute on function public.get_hero_connections(text, text, integer)
  to anon, authenticated, service_role;

-- Generation ledger: marks heroes already processed (including those that yielded
-- zero connections, so we don't reprocess them). Mirrors heroes.comicvine_status.
alter table public.heroes
  add column if not exists relationships_ai_status text;
```

```typescript
import { supabase } from '../supabase';
import type { RelatedHeroCard } from './heroes';

export type ConnectionKind = 'love_interest' | 'mentor' | 'protege' | 'rival';

export interface HeroConnections {
  loveInterests: RelatedHeroCard[];
  mentors: RelatedHeroCard[];
  proteges: RelatedHeroCard[];
  rivals: RelatedHeroCard[];
}

const EMPTY: HeroConnections = {
  loveInterests: [],
  mentors: [],
  proteges: [],
  rivals: [],
};

async function fetchKind(heroId: string, kind: ConnectionKind): Promise<RelatedHeroCard[]> {
  const { data, error } = await supabase.rpc('get_hero_connections', {
    p_hero_id: heroId,
    p_kind: kind,
    p_limit: 24,
  });
  if (error) {
    console.warn('[getConnections] error:', error.message);
    return [];
  }
  return (data ?? []) as RelatedHeroCard[];
}

/**
 * Richer relationship kinds (love interest / mentor / protege / rival) for a hero,
 * from the authored hero_connections table via get_hero_connections. Ranked by the
 * related hero's popularity.
 */
export async function getConnections(heroId: string): Promise<HeroConnections> {
  if (!heroId) return EMPTY;
  const [loveInterests, mentors, proteges, rivals] = await Promise.all([
    fetchKind(heroId, 'love_interest'),
    fetchKind(heroId, 'mentor'),
    fetchKind(heroId, 'protege'),
    fetchKind(heroId, 'rival'),
  ]);
  return { loveInterests, mentors, proteges, rivals };
}
```

### Task 5: `ConnectionsSection` component

**Files:**
- Create: `src/components/ConnectionsSection.tsx`

Takes the four `RelatedHeroCard[]` lists, builds the `names` + `heroMap` inputs `RelatedHeroStrip` expects, renders one strip per non-empty kind, returns `null` when all empty so the caller can place it unconditionally. The caller wraps it with its existing section header.

- [ ] **Step 1: Create the component**

```typescript
import { View, StyleSheet } from 'react-native';
import { RelatedHeroStrip } from './RelatedHeroStrip';
import type { RelatedHeroCard } from '../lib/db/heroes';
import type { HeroConnections } from '../lib/db/relationships';

/**
 * Richer-relationship strips (love interest / mentor / protege / rival) for the
 * character screen. Each list is already resolved to hero cards by getConnections,
 * so we adapt to RelatedHeroStrip's (names + heroMap) API. Null when nothing to show.
 */
export function ConnectionsSection({
  connections,
  onPressHero,
}: {
  connections: HeroConnections;
  onPressHero: (hero: RelatedHeroCard) => void;
}) {
  const { loveInterests, mentors, proteges, rivals } = connections;
  const total =
    loveInterests.length + mentors.length + proteges.length + rivals.length;
  if (total === 0) return null;

  const strips: {
    key: string;
    label: string;
    kind: 'love_interest' | 'mentor' | 'protege' | 'rival';
    cards: RelatedHeroCard[];
  }[] = [
    { key: 'love', label: 'Love Interests', kind: 'love_interest', cards: loveInterests },
    { key: 'mentor', label: 'Mentors', kind: 'mentor', cards: mentors },
    { key: 'protege', label: 'Proteges', kind: 'protege', cards: proteges },
    { key: 'rival', label: 'Rivals', kind: 'rival', cards: rivals },
  ];

  return (
    <View style={styles.block}>
      {strips.map(({ key, label, kind, cards }) =>
        cards.length ? (
          <RelatedHeroStrip
            key={key}
            label={label}
            names={cards.map((c) => c.name)}
            heroMap={new Map(cards.map((c) => [c.name, c]))}
            kind={kind}
            onPressHero={onPressHero}
          />
        ) : null,
      )}
    </View>
  );
}

const styles = StyleSheet.create({
  block: { marginTop: 2 },
});
```

### Task 8: Generation runbook + first batch

**Files:**
- Create: `docs/superpowers/runbooks/relationships-ai-generation.md`

Generation is an in-tab Claude activity, not shipped code. This task documents the repeatable procedure and runs it once on a small batch to validate the UI end-to-end.

- [ ] **Step 1: Write the runbook**

Create `docs/superpowers/runbooks/relationships-ai-generation.md` documenting the loop:

1. **Pick a batch** — `execute_sql`:
   ```sql
   select id, name, publisher, issue_count, deck, description
   from heroes
   where relationships_ai_status is null
   order by issue_count desc nulls last
   limit 25;
   ```
2. **Generate** — for each hero, from its `deck`/`description` + known character
   knowledge, propose edges of `love_interest` / `mentor` / `protege` / `rival`, each
   with confidence 0–1. **Do not** emit `love_interest` for pairs that are canonically
   family/married (that belongs to `hero_relatives`, not here).
3. **Filter + resolve** — drop confidence < 0.7; resolve each related name to a hero
   `id` (`select id, name, issue_count from heroes where name = any($names)`); drop
   unresolved names.
4. **Rank** — within each `(hero_id, kind)`, order by the related hero's `issue_count`
   desc; `rank` = 1-based index.
5. **Write** — both directed edges per relationship (`mentor`→`protege` inverse;
   `love_interest`/`rival` symmetric), into `hero_connections`:
   ```sql
   insert into hero_connections (hero_id, related_id, kind, rank, confidence, cross_universe)
   values (...)
   on conflict (hero_id, kind, related_id) do nothing;
   ```
   (`cross_universe` = subject.publisher is distinct from related.publisher.)
6. **Mark done** — `update heroes set relationships_ai_status = 'done' where id = any($batchIds);`
   (Mark every hero in the batch, including those that produced zero edges.)

- [ ] **Step 2: Run one batch (top ~25 heroes)**

Execute the loop via `mcp__supabase__execute_sql`. Keep edges high-precision —
canonical relationships only (e.g. love_interest: Spider-Man↔Mary Jane;
mentor/protege: Batman→Robin; rival: Spider-Man↔Venom).
